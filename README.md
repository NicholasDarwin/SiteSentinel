# SiteSentinel

**A second opinion on any website, with the evidence attached.**

Paste in a URL and SiteSentinel runs nine inspectors in parallel: HTTPS and security headers, phishing and malware signals, DNS, WHOIS age, outbound links, performance, accessibility and SEO. It scores each category out of 100 and combines them into one weighted score.

Each finding shows how it was reached. Every check records:

- **What was observed**: the response header, the HTML snippet and its line, or the script and the host it loads from
- **What it cost**: the points deducted and the most it could have cost
- **Why it matters** and **how to fix it**, with a config example where one helps
- **How sure it is**: a confidence level, plus a note when the result could be a false positive

If a result looks wrong, you can check it against the evidence yourself.

## Quick start

Requires **Node.js 18+**.

```bash
git clone https://github.com/NicholasDarwin/SiteSentinel.git
cd SiteSentinel
npm install
cp .env.example .env     # optional
npm start                # http://localhost:3000
```

One Express server hosts both the interface and the API. The `docs/` folder is also published to GitHub Pages as a static site, but scans need the Node server, so run it locally to try one.

### Configuration

All settings are optional.

| Variable | Default | What it does |
| --- | --- | --- |
| `PORT` | `3000` | Port the server listens on. |
| `GOOGLE_SAFE_BROWSING_API_KEY` | none | Adds Google Safe Browsing lookups to Safety & Threats. Without a key, that check uses local heuristics only and says so in its evidence. |
| `ENABLE_AI` | `0` | Set to `1` to turn on the report summary and the "Ask about this report" panel. Both are generated by rules from the report data. No external model or API key is involved. |
| `NODE_ENV` | `development` | In `production`, internal error messages are hidden from API responses. |

## What it inspects

| Inspector | Weight | What it looks at |
| --- | :---: | --- |
| **Security & HTTPS** | 3 | HTTPS, TLS version, HSTS, CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, scam redirects |
| **Safety & Threats** | 3 | Google Safe Browsing, phishing and typosquat patterns, credential-harvesting forms, obfuscated JavaScript, deceptive downloads, mixed content, iframes, third-party scripts, known security-test URLs |
| **DNS & Domain** | 2 | Resolution, name server redundancy, IPv6, CAA, SPF, DMARC, MX |
| **Link Analysis** | 2 | Outbound link density and suspicious redirect chains |
| **External Links** | 1.5 | Every outbound link and script-embedded URL, each graded safe, warning, unsafe or broken |
| **Performance** | 1.5 | Load time, response size, compression, caching, HTTP version, keep-alive, redirect hops |
| **Accessibility (WCAG 2.1)** | 1.5 | Alt text, form labels, contrast, heading order, landmarks, page language, skip links, keyboard access |
| **SEO & Metadata** | 1 | Title, meta description, H1, canonical URL, Open Graph, structured data, viewport, robots, favicon |
| **WHOIS & Domain Info** | 1 | Registrar, domain age, expiry, status codes, name servers, DNSSEC |

The [`docs/agents/`](docs/agents) and [`docs/safety/`](docs/safety) pages explain each inspector and safety check in more depth.

## How scoring works

Every weight lives in one file, [`src/utils/score-calculator.util.js`](src/utils/score-calculator.util.js), so retuning the scoring is a one-file change.

**Within a category**

1. The category starts at **100**.
2. Each check has a severity worth a set number of points: critical **35**, high **20**, medium **10**, low **5**, info **0**.
3. A failed check deducts its full value. A warning deducts half.
4. Ordinary deductions can't take a category below **15**, so one or two findings never read as total failure.

**Across categories**

- The overall score is a **weighted average** of the categories, using the weights in the table above.
- A category that errored or couldn't run is **left out** instead of counted as zero.
- If fewer than a third of the categories could be analyzed (for example, the site is unreachable), the report says **Unable to Analyze** instead of showing a rating that could mislead.

**Overrides**

- A confirmed, high-confidence malware or phishing match sets Safety & Threats and the overall score to **0**.
- Suspicious redirect chains cap the overall score at **25**.

| Score | Label |
| --- | --- |
| 90–100 | Excellent |
| 75–89 | Good |
| 60–74 | Fair |
| 45–59 | Poor |
| 0–44 | Critical |

## Safeguards

SiteSentinel fetches URLs that users submit and follows redirects from sites it doesn't trust, so it guards against being used as an attack proxy:

- **SSRF protection.** Hostnames are resolved before any connection. Loopback, private ranges (10/8, 172.16/12, 192.168/16), carrier-grade NAT, link-local, cloud metadata (`169.254.169.254`), multicast and the IPv6 equivalents are all refused. The check runs again on **every redirect hop**, which defeats DNS rebinding and redirect tricks.
- **Passive inspection only.** It makes the same requests a normal browser visit would. It doesn't scan ports, guess credentials, submit forms or send attack payloads.
- **Honest unknowns.** When a lookup fails, the check reports "unable to determine", never "safe".
- **Security-test recognition.** Known test URLs such as Google's Safe Browsing test pages are flagged as the threats they imitate, so a scanner bug can't pass them as clean. They are labelled as test resources in the evidence.

Only inspect sites you are allowed to.

## API

### `POST /api/analyze`

```bash
curl -X POST http://localhost:3000/api/analyze \
  -H "Content-Type: application/json" \
  -d '{ "url": "example.com" }'
```

Example response (shortened):

```json
{
  "success": true,
  "url": "https://example.com/",
  "timestamp": "2026-10-14T12:00:00.000Z",
  "overall": {
    "score": 82,
    "label": "Good",
    "unableToAnalyze": false,
    "breakdown": { "includedCategories": 9, "totalCategories": 9, "excludedCategories": [] }
  },
  "categories": [
    {
      "category": "Security & HTTPS",
      "score": 90,
      "checks": [
        {
          "name": "Content Security Policy (CSP)",
          "status": "warn",
          "severity": "medium",
          "maxPoints": 10,
          "pointsDeducted": 5,
          "confidence": "high",
          "description": "CSP not configured (recommended but not required)",
          "evidence": [{ "type": "headers", "highlightHeader": "content-security-policy", "present": false }],
          "fix": "Add a Content-Security-Policy header, e.g. in nginx: ..."
        }
      ]
    }
  ]
}
```

A URL that is malformed or points at a private network address gets a `400` with an `error` message.

### Other endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/health`, `/api/health` | Server status and version |
| `GET` | `/api/ai/enabled` | Whether the report summary features are on |
| `POST` | `/api/ai/quick-assessment` | Short summary for a report: `{ report }` |
| `POST` | `/api/ai/security-insights` | Prioritized findings and a fix checklist: `{ report, question? }` |

## Architecture

```
            ┌────────────────────────────────────────────┐
 browser ──▶│  Express  (src/server.js)                  │
            │   ├─ static UI          docs/              │
            │   └─ POST /api/analyze                     │
            │        │  validate URL + SSRF pre-check    │
            │        ▼                                   │
            │   9 inspectors run in parallel             │
            │   (src/checks/*.check.js)                  │
            │        │  each returns checks + evidence   │
            │        ▼                                   │
            │   score-calculator → weighted report       │
            └────────────────────────────────────────────┘
```

```
src/
├── server.js                    Express app, static hosting, error handling
├── routes/
│   ├── analyze.route.js         Validation, SSRF pre-check, parallel run, scoring
│   └── ai.route.js              Optional rule-based summaries
├── checks/                      One module per inspector
└── utils/
    ├── score-calculator.util.js All severity and category weights
    ├── ssrf-guard.util.js       Blocks private/internal destinations per hop
    ├── http.util.js             Axios client wired to the SSRF guard
    ├── evidence.util.js         Builds structured evidence for findings
    ├── security-test-signatures.util.js  Registry of known test URLs
    └── domain.util.js           Registrable-domain parsing (tldts)
docs/
├── index.html, app.js           Interface and results view
├── js/seal.js                   Draws a guilloche seal unique to each hostname
├── agents/, safety/             Explainer pages for each inspector and check
└── styles.css                   Design system
```

An inspector that throws doesn't break the scan. Its failure becomes an `error` check in that category, the category drops out of the score, and the other eight still report.

## Testing

```bash
npm test
```

There are 77 Jest tests across 8 suites. They cover the scoring math, the SSRF guard (private ranges, IPv4-mapped IPv6, per-hop enforcement), security-test signatures, domain parsing, the analyze route, and detection edge cases in the safety, link and external-link inspectors, including regression tests for past false positives and misses.

## Tech stack

- **Runtime:** Node.js, Express
- **Fetching and parsing:** Axios, Cheerio, Puppeteer (for pages that only render in a real browser), tldts
- **Frontend:** Plain HTML, CSS and JavaScript, no build step
- **Testing:** Jest
